# Mall 商家端需求分析与开发指导书

> 版本：v1.0  
> 编写目的：为 Mall 商家端后续开发提供统一的需求、数据归属、接口和验收依据。  
> 重要约束：不改变当前项目的微服务划分和前端模块化结构，不新建独立的 `mall-seller` 微服务，不将用户端、管理员端和商家端合并到同一套页面中。

---

## 1. 建设目标

商家端服务于 `role = 1` 的商家账号，使商家可以在自己的工作台完成：

1. 查看经营概况。
2. 管理自己店铺的商品和 SKU。
3. 查看和维护自己商品对应的库存。
4. 查看属于自己的订单商品。
5. 对已支付订单执行发货。
6. 维护店铺基本资料。

平台管理员仍然拥有全平台管理权限；买家仍然只使用商城前台。商家端的核心原则是：

> 商家可以管理自己的数据，但不能通过修改请求参数、商品 ID 或订单 ID 访问其他商家的数据。

## 2. 当前项目现状

### 2.1 已有技术和目录

前端继续使用：

- Vue 3
- Vite
- Vue Router
- Pinia
- Element Plus
- Axios 公共请求封装

后端继续使用当前微服务：

| 模块 | 端口/职责 | 商家端复用内容 |
|---|---|---|
| `mall-gateway` | 网关、JWT 校验、路由转发 | 统一鉴权和 `/api/seller/**` 转发 |
| `mall-user` | 用户、登录、地址 | 商家身份和店铺资料 |
| `mall-product` | 分类、SPU、SKU | 商家商品和 SKU |
| `mall-inventory` | 库存、库存日志 | 商家库存查询和补货 |
| `mall-order` | 订单、订单项 | 商家订单和发货 |
| `mall-payment` | 支付、退款 | 商家只读查看与订单关联信息，退款仍由平台处理 |
| `mall-front` | 三端前端代码 | 在现有 `src/modules/seller` 内扩展 |

当前前端已经存在：

```text
mall-front/src/modules/seller/
├─ layouts/
│  └─ SellerLayout.vue
└─ views/
   └─ SellerDashboard.vue
```

当前商家布局和首页已经可以访问，但商品、库存、订单菜单仍处于禁用状态。后续只在现有目录下增加页面、API 和组件，不移动既有用户端、管理员端文件。

### 2.2 角色约定

| `role` | 角色 | 权限范围 |
|---:|---|---|
| 0 | 买家 | 浏览、购物车、下单、支付、个人订单 |
| 1 | 商家 | 自己店铺的商品、库存、订单、发货 |
| 2 | 管理员 | 全平台用户、商品、库存、订单、支付和退款 |

登录成功后前端跳转规则保持不变：

```text
role = 0  -> /
role = 1  -> /seller/dashboard
role = 2  -> /admin/dashboard
```

## 3. 结构约束与开发原则

### 3.1 不改变项目结构

不能采取以下方式：

- 新建 `mall-seller` 顶层后端微服务。
- 将商家页面移动到 `src/views` 并破坏现有模块划分。
- 复制一套 Axios、Token、路由守卫或 Element Plus 初始化代码。
- 让商家直接调用管理员接口并仅靠前端隐藏字段限制权限。
- 让前端传入 `sellerId` 后端据此判断数据归属。

推荐的扩展位置：

```text
mall-front/src/modules/seller/
├─ api/
│  ├─ dashboard.js
│  ├─ product.js
│  ├─ inventory.js
│  ├─ order.js
│  └─ shop.js
├─ components/
│  ├─ ProductForm.vue
│  ├─ SkuEditor.vue
│  ├─ StockAdjustDialog.vue
│  └─ ShipOrderDialog.vue
├─ layouts/
│  └─ SellerLayout.vue
└─ views/
   ├─ SellerDashboard.vue
   ├─ SellerProductList.vue
   ├─ SellerProductForm.vue
   ├─ SellerInventory.vue
   ├─ SellerOrderList.vue
   ├─ SellerOrderDetail.vue
   └─ SellerShopProfile.vue
```

后端不增加新的服务，只在对应服务内增加商家专用 Controller、DTO、Service 方法和 Mapper 查询：

```text
mall-product/.../controller/SellerProductController.java
mall-inventory/.../controller/SellerInventoryController.java
mall-order/.../controller/SellerOrderController.java
mall-user/.../controller/SellerShopController.java
```

这些文件是现有微服务内部的扩展，不改变微服务边界。

### 3.2 权限必须前后端同时控制

前端路由守卫负责页面体验，后端负责真正的安全控制：

```text
请求 -> Gateway 校验 JWT
     -> 注入 X-User-Id 和 X-User-Role
     -> SellerController 校验 role = 1
     -> Service 根据 X-User-Id 查询 seller_id
     -> Mapper 使用 seller_id 过滤数据
```

后端不得信任以下参数作为当前商家身份：

- URL 中的 `sellerId`。
- 请求体中的 `sellerId`。
- 前端 localStorage 中保存的用户角色。

当前登录商家 ID 必须从网关传入的 `X-User-Id` 获取。

## 4. 商家端功能需求

## 4.1 商家登录与工作台

### 页面需求

- 商家与买家共用现有登录页面和登录接口。
- 商家登录成功后进入 `/seller/dashboard`。
- 商家访问 `/admin/**` 时跳转商城首页。
- 买家访问 `/seller/**` 时跳转商城首页。
- 未登录访问商家页面时跳转 `/login`，并保留原始路径。
- 商家端顶部提供“进入商城”和“退出登录”。

### 验收标准

- 商家刷新页面后仍停留在商家端。
- 删除或伪造 localStorage 中的角色后，后端接口仍不能越权。
- 买家直接访问 `/seller/products` 返回到商城首页。

## 4.2 店铺资料

店铺资料是商品归属和商家展示的基础。第一阶段只做必要字段，不引入复杂的入驻审核和结算功能。

### 字段

| 字段 | 必填 | 说明 |
|---|---|---|
| 店铺名称 | 是 | 商家展示名称，建议唯一 |
| 店铺 Logo | 否 | 图片地址，当前项目没有文件服务时先保存 URL |
| 联系人 | 是 | 店铺业务联系人 |
| 联系电话 | 是 | 发货和平台联系使用 |
| 店铺简介 | 否 | 前台店铺简介 |
| 店铺状态 | 是 | 0-停用，1-正常，2-待审核（如启用审核流程） |

### 规则

- 一个商家账号默认对应一个店铺。
- 商家不能修改 `seller_id`。
- 店铺被管理员停用后，商家不能新增商品、上架商品和发货。
- 店铺资料修改必须记录 `update_time`。

### 接口建议

```http
GET  /api/seller/shop
PUT  /api/seller/shop
```

## 4.3 商品管理

### 功能范围

- 商品分页查询。
- 按商品名称、分类、状态筛选。
- 新增 SPU。
- 编辑 SPU 基本信息。
- 新增、编辑、禁用 SKU。
- 设置价格、规格、图片和初始库存。
- 商品上架、下架。
- 查看商品关联库存。

### 商品状态

继续兼容当前项目的商品状态：

| 状态 | 值 | 说明 |
|---|---:|---|
| 下架 | 0 | 买家端不可购买，商家可编辑 |
| 上架 | 1 | 买家端可展示和购买 |

如后续需要管理员审核，再增加独立的 `audit_status` 字段，不要改变现有 `status` 的含义。

### 商品归属规则

- `product_spu` 必须增加 `seller_id`，必要时增加 `shop_id`。
- SKU 通过所属 SPU 继承商家归属，不必重复保存 seller_id。
- 商家商品列表必须使用 `WHERE spu.seller_id = 当前用户ID`。
- 编辑、上下架、删除前必须再次校验商品属于当前商家。
- 已被订单引用的 SPU/SKU 不做物理删除，使用下架或禁用。
- 管理员可以查看和维护全部商品；商家只能查看自己的商品。

### 接口建议

```http
GET  /api/seller/products/page?pageNum=1&pageSize=20&keyword=&categoryId=&status=
GET  /api/seller/products/{spuId}
POST /api/seller/products
PUT  /api/seller/products/{spuId}
PUT  /api/seller/products/{spuId}/status
GET  /api/seller/products/{spuId}/skus
POST /api/seller/products/{spuId}/skus
PUT  /api/seller/skus/{skuId}
PUT  /api/seller/skus/{skuId}/status
```

新增和编辑请求中不允许由前端提交可信的 `sellerId`；后端从登录用户身份设置归属。

## 4.4 库存管理

### 功能范围

- 查看自己商品的 SKU 库存。
- 查看总库存、锁定库存、可用库存和安全库存。
- 补充库存。
- 修改安全库存。
- 查看库存变更日志。
- 对低于安全库存的 SKU 进行预警展示。

### 库存规则

```text
可用库存 = 总库存 - 锁定库存
库存预警 = 可用库存 <= 安全库存
```

- 商家补货数量必须大于 0。
- 补货、初始化和安全库存修改必须有操作日志。
- 下单锁定、支付扣减、取消释放由订单/支付流程完成，商家页面不能直接模拟这些交易动作。
- 商家库存查询必须关联 `product_sku -> product_spu -> seller_id` 过滤。
- 不能通过修改 SKU ID 操作其他商家的库存。

### 接口建议

```http
GET /api/seller/inventory?pageNum=1&pageSize=20&keyword=&warningOnly=false
PUT /api/seller/inventory/{skuId}/add
PUT /api/seller/inventory/{skuId}/safety-stock
GET /api/seller/inventory/{skuId}/logs
```

补货请求示例：

```json
{
  "quantity": 100,
  "remark": "采购入库"
}
```

## 4.5 订单管理与发货

### 功能范围

- 查看包含自己商品的订单。
- 按订单号、买家、订单状态、创建时间筛选。
- 查看订单商品、数量、金额、收货信息和备注。
- 查看支付状态和支付时间。
- 对已支付订单填写物流公司和运单号。
- 查看发货时间、物流单号和订单状态。
- 不允许商家取消买家订单、修改订单金额或处理退款。

### 订单状态

继续使用当前订单状态：

| 状态 | 值 | 商家可执行操作 |
|---|---:|---|
| 待支付 | 0 | 只能查看，不能发货 |
| 已支付 | 1 | 可以发货 |
| 已发货 | 2 | 查看物流信息 |
| 已完成 | 3 | 查看订单 |
| 已取消 | 4 | 只能查看 |

### 多商家订单必须提前处理

当前订单表是买家订单，订单项保存 SPU/SKU 信息。如果一个订单允许同时购买多个商家的商品，不能简单地让一个商家把整笔订单标记为已发货，否则会影响其他商家。

推荐方案：

1. `order_item` 增加 `seller_id` 和 `seller_order_id`。
2. 增加商家子订单表 `seller_order_t`，保存 `order_id`、`seller_id`、子订单金额、子订单状态、物流信息和发货时间。
3. 商家只操作自己的子订单。
4. 买家主订单在所有子订单完成后再变为已完成。
5. 退款时按主订单和子订单的商品归属计算可退金额。

本项目允许买家一次结算多个商家的商品：当前主订单负责总金额和一次支付，`order_item.seller_id` 负责固化每件商品的商家归属。在商家端开放发货前，必须完成 `seller_order_t` 子订单实现；在此之前不得向商家开放对主订单状态的修改接口，避免任一商家操作整笔混合订单。

### 接口建议

```http
GET /api/seller/orders/page?pageNum=1&pageSize=20&orderNo=&status=&startTime=&endTime=
GET /api/seller/orders/{sellerOrderId}
PUT /api/seller/orders/{sellerOrderId}/ship
```

发货请求：

```json
{
  "shippingCompany": "顺丰速运",
  "trackingNo": "SF1234567890"
}
```

发货接口必须使用事务，并且同时完成：

1. 校验子订单属于当前商家。
2. 校验状态为已支付。
3. 校验物流公司和运单号非空。
4. 写入物流信息和发货时间。
5. 更新子订单状态为已发货。

## 4.6 商家经营概览

首页只展示当前商家的统计数据，不展示平台全量数据：

- 商品总数、上架商品数、下架商品数。
- SKU 总数、库存预警数。
- 待发货订单数、今日订单数、今日销售额。
- 最近订单。
- 库存预警列表。

### 接口建议

```http
GET /api/seller/dashboard/overview
GET /api/seller/dashboard/recent-orders?limit=10
GET /api/seller/dashboard/stock-alerts?limit=10
```

所有金额和订单数量都必须按当前 `seller_id` 过滤，不能复用管理员首页的全平台统计接口。

## 5. 数据库设计建议

### 5.1 店铺表 `shop_t`

```text
id              BIGINT PRIMARY KEY
seller_id       BIGINT NOT NULL UNIQUE
shop_name       VARCHAR(128) NOT NULL
logo            VARCHAR(500) NULL
contact_name    VARCHAR(64) NOT NULL
contact_phone   VARCHAR(32) NOT NULL
description     VARCHAR(500) NULL
status          TINYINT NOT NULL DEFAULT 1
create_time     DATETIME NOT NULL
update_time     DATETIME NOT NULL
```

### 5.2 商品归属字段

在 `product_spu` 增加：

```text
seller_id BIGINT NOT NULL
shop_id   BIGINT NULL
```

建议建立索引：

```text
idx_spu_seller_status (seller_id, status)
idx_spu_shop (shop_id)
```

现有历史商品迁移时必须明确归属：

- 平台自营商品：绑定平台自营账号或管理员维护的特殊店铺。
- 无法确认归属的商品：暂时设置为下架，禁止直接展示。
- 不允许把所有历史商品默认分配给第一个商家。

### 5.3 订单归属字段

最小改造：

```text
order_item.seller_id BIGINT NOT NULL
```

推荐完整改造：

```text
seller_order_t
├─ id
├─ order_id
├─ seller_id
├─ total_amount
├─ status
├─ shipping_company
├─ tracking_no
├─ ship_time
├─ receive_time
├─ create_time
└─ update_time
```

索引建议：

```text
idx_order_item_seller (seller_id, order_id)
idx_seller_order_seller_status (seller_id, status, create_time)
```

### 5.4 数据一致性要求

- 商品归属、库存归属、订单归属必须来自同一条商品关系链。
- 订单生成时复制 `seller_id`，不能只依赖后续商品表查询。
- 商品转让功能未设计完成前，不允许修改商品的 `seller_id`。
- 店铺停用不删除商品和订单历史。
- 已有支付、退款和订单数据不能因为增加商家字段而丢失。

### 6.1 统一返回格式

继续使用项目已有的 `Result<T>`：

```json

  "code": 200,
```

```text

```

## 7. 前端页面和路由设计

在现有 `/seller` 路由下增加子路由：

```text
/seller/dashboard       经营概览
/seller/products         我的商品
/seller/products/create  新增商品
/seller/products/:id     编辑商品
/seller/inventory        库存管理
/seller/orders           店铺订单
/seller/orders/:id       订单详情
/seller/shop             店铺资料
```

`SellerLayout.vue` 继续作为父布局，左侧菜单仅增加路由项，不新增第二套布局。菜单建议顺序：

```text
经营概览
我的商品
库存管理
店铺订单
店铺资料
```

页面交互要求：

- 列表页面统一提供查询、重置、分页和加载状态。
- 删除、下架、补货、发货等动作必须二次确认。
- 接口失败时使用现有 Axios 响应拦截器提示。
- 表单关闭后清理旧数据，避免编辑上一个商品时残留字段。
- 商家端不要显示平台全量统计、管理员操作入口和退款审核按钮。

## 8. 推荐开发顺序

严格按以下顺序实施，避免先写页面、后发现数据无法隔离：

### 阶段一：数据归属基础

- 确认 `user.role = 1` 商家身份。
- 新增店铺表和商品 `seller_id`。
- 为历史商品制定迁移方案。
- 订单生成时保存订单项商家归属。
- 确定是否采用 `seller_order_t` 子订单。

### 阶段二：后端权限和查询

- 新增商家专用 Controller，放在现有服务内。
- 所有查询使用网关传入的 `X-User-Id`。
- 增加商品、库存、订单的商家过滤 SQL。
- 补充非法 ID、跨商家 ID 的 403/404 处理。
- 先用接口测试验证数据隔离，再做页面。

### 阶段三：商家商品管理

- 打通商品列表。
- 实现 SPU 新增和编辑。
- 实现 SKU 新增、编辑和状态管理。
- 实现商品上下架。
- 验证商家 A 不能看到或修改商家 B 的商品。

### 阶段四：库存管理

- 打通库存列表和预警。
- 实现补货和安全库存设置。
- 校验库存日志和事务。
- 验证库存变化不影响其他商家 SKU。

### 阶段五：订单和发货

- 打通商家订单列表和详情。
- 完成支付状态、支付时间展示。
- 实现物流公司、运单号和发货时间保存。
- 处理多商家订单隔离。
- 验证发货后买家端状态同步。

### 阶段六：经营概览和体验优化

- 接入商家统计接口。
- 增加最近订单和库存预警。
- 完善空数据、加载失败、重复提交和移动端布局。

## 9. 关键验收标准

### 权限验收

- 买家不能访问任何 `/seller/**` 页面。
- 买家不能调用任何 `/api/seller/**` 接口。
- 商家不能访问 `/api/admin/**` 接口。
- 商家 A 无法通过修改商品 ID、SKU ID、订单 ID 读取商家 B 的数据。
- 退出登录后 Token 被清除，浏览器后退不能继续访问商家页面。

### 商品验收

- 商家新增商品后默认归属于自己。
- 商家只看到自己的商品。
- 商品下架后买家端不可购买。
- 已有关联订单的 SKU 不允许物理删除。

### 库存验收

- 补货数量为 0 或负数时拒绝。
- 补货成功后总库存和可用库存正确增加。
- 每一次人工补货都有库存日志。
- 低库存商品能够在商家首页显示。

### 订单验收

- 商家只能看到包含自己商品的订单或子订单。
- 待支付订单不能发货。
- 发货必须填写物流公司和运单号。
- 发货成功后记录发货时间，买家端能看到发货状态。
- 退款审核仍由管理员完成，商家端不提供退款审批按钮。

### 回归验收

- 买家注册、登录、浏览、购物车、下单、支付和订单列表功能不受影响。
- 管理员用户、商品、订单、库存、支付和退款功能不受影响。
- Nacos、网关和已有服务启动方式不改变。

## 10. 启动和联调说明

商家端不是独立应用，不需要启动新的服务。开发时仍然启动：

1. Nacos。
2. `mall-user`。
3. `mall-product`。
4. `mall-inventory`。
5. `mall-order`。
6. `mall-payment`。
7. `mall-gateway`。
8. `mall-front`。

如果只修改商家页面，只需重载前端；如果修改用户、商品、库存或订单后端代码，需要重启对应微服务。新增 `/api/seller/**` 路由规则或网关配置时，需要重启网关。

联调建议使用两个商家账号：

```text
商家 A：只创建商品 A、库存 A
商家 B：只创建商品 B、库存 B
```

使用商家 A 登录后，分别尝试访问商品 B、SKU B 和订单 B 的 ID，必须得到无权限或不存在的结果。测试结束后再使用买家账号验证前台商品和订单流程。

## 11. 暂不实现的功能

以下功能不属于商家端第一阶段，避免扩大范围：

- 商家入驻审核和资质认证。
- 多级商家员工账号。
- 商家结算、佣金和提现。
- 优惠券、分销、营销活动。
- 第三方物流实时轨迹。
- 商家自主退款审批。
- 多仓库和区域库存。

这些功能需要新的业务模型，后续应单独进行需求评审，不应直接塞入当前商品、库存或订单接口。

## 12. 开发完成定义

满足以下条件后，才认为商家端第一阶段完成：

- 商家可以登录并进入独立工作台。
- 商品、库存、订单和发货功能形成闭环。
- 所有商家数据都按 `seller_id` 隔离。
- 商家可以操作自己的商品，但不能操作管理员或其他商家的数据。
- 买家端和管理员端原有功能通过回归测试。
- 前端构建成功，后端相关服务编译成功。
- 接口权限、混合订单、库存并发和异常提示均有测试记录。
