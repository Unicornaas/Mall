# Mall 管理员端需求分析与开发指导书

> 版本：v1.0  
> 适用范围：现有 Mall 用户端已可注册、登录、浏览商品、加入购物车、下单、支付的基础上，建设平台管理员端（Admin）。  
> 目标：先交付可运营的后台管理闭环，再逐步扩展数据分析、风控和系统配置能力。

---

## 1. 项目现状与建设边界

### 1.1 已有能力

后端已按微服务拆分为用户、商品、订单、购物车、库存、支付和网关模块；网关会解析 JWT，并向下游传递 `X-User-Id` 与 `X-User-Role`。角色约定如下：

| role 值 | 角色 | 管理端含义 |
|---:|---|---|
| 0 | 买家 | 无后台权限 |
| 1 | 卖家 | 仅商品、库存等业务权限（后续可独立为商家端） |
| 2 | 管理员 | 可进入平台管理员端 |

当前用户端采用 Vue 3 + Vite + Element Plus + Pinia；后端已有分类、SPU、SKU、库存、支付记录等基础实体和部分维护接口。

### 1.2 当前缺口

管理员端不是单纯新增几个页面，还需要补齐以下能力：

1. 前端没有 `/admin` 路由、后台布局、权限守卫和管理菜单。
2. 用户服务缺少管理员分页查询用户、启停用户接口。
3. 订单服务缺少平台订单分页、订单详情管理、发货/确认收货、按状态筛选。
4. 商品服务缺少后台分页检索、完整审核/上下架、品牌管理等能力。
5. 缺少经营统计接口和首页看板数据。
6. 管理操作缺少审计日志；退款处理、库存变更等关键动作需要可追溯。

### 1.3 本期不纳入范围

以下能力建议留到第二阶段，不阻塞管理员端首版上线：

- 多租户商家入驻、店铺结算与佣金。
- 优惠券、秒杀、拼团、会员积分。
- 第三方物流实时轨迹。
- ES 搜索、消息队列、数据仓库、复杂报表。
- 多级管理员、细粒度菜单/按钮权限配置。

## 2. 管理员端目标与角色模型

管理员端的目标是让平台管理员完成“看数据、管用户、管商品、管订单、管库存、管退款”六类工作。

本期仅设置一个平台管理员角色：`role = 2`。所有 `/admin/**` 页面和 `/api/admin/**` 接口必须拒绝非管理员访问；不要仅在前端隐藏菜单，后端必须再次校验 `X-User-Role = 2`。

推荐的权限模型：

```text
登录成功
  ├─ role = 0：跳转用户商城首页
  ├─ role = 1：暂时跳转用户商城首页（后续接入商家端）
  └─ role = 2：可进入 /admin/dashboard
```

## 3. 功能需求

### 3.1 后台登录与权限控制

#### 需求

- 管理员与普通用户共用现有登录接口。
- 登录返回的用户信息必须包含 `role`。
- 管理员访问 `/admin/**` 时，前端路由守卫检查 Token 和 `user.role === 2`。
- 后端所有管理接口统一使用 `/api/admin/**` 前缀，并校验网关注入的 `X-User-Role`。
- 非管理员访问后台页面跳回商城首页；非管理员调用后台接口返回 `403`。

#### 验收标准

- 买家输入 `/admin/dashboard` 不可进入。
- 买家直接调用 `/api/admin/**` 得到统一格式的 403 响应。
- 管理员登录后刷新页面仍可保持后台登录状态。

### 3.2 管理首页（数据看板）

#### 页面内容

- 今日订单数、今日支付金额、待支付订单数、待处理退款数。
- 用户总数、今日新增用户数、上架商品数、库存预警 SKU 数。
- 最近 7 天订单金额趋势图。
- 最新订单列表（最近 10 条）。
- 库存预警列表（可用库存小于等于安全库存）。

#### 接口建议

```http
GET /api/admin/dashboard/overview
GET /api/admin/dashboard/order-trend?days=7
GET /api/admin/dashboard/latest-orders?limit=10
GET /api/admin/dashboard/stock-alerts?limit=10
```

#### 数据口径

| 指标 | 口径 |
|---|---|
| 今日订单数 | 当天创建的订单数，含待支付和已支付 |
| 今日支付金额 | 当天支付成功订单的 `total_amount` 总和 |
| 待支付订单 | `status = 0` |
| 已支付订单 | `status = 1` |
| 已取消订单 | `status = 4` |
| 库存预警 | `available_stock <= safety_stock` |

### 3.3 用户管理

#### 功能

- 用户分页列表：用户名、手机号、邮箱、角色、状态、注册时间。
- 按用户名、手机号、状态、角色筛选。
- 查看用户详情与地址数量、订单数量、累计消费额。
- 启用/禁用用户。
- 管理员不得禁用自己；被禁用用户不可登录或继续下单。

#### 接口建议

```http
GET /api/admin/users?pageNum=1&pageSize=20&keyword=&status=&role=
GET /api/admin/users/{id}
PUT /api/admin/users/{id}/status
```

状态更新请求：

```json
{ "status": 0 }
```

#### 数据库与服务修改

- 复用 `user.status`、`user.role` 字段。
- `UserMapper` 增加后台分页查询、按 ID 更新状态、统计用户订单数/消费额的方法。
- 登录与网关鉴权之后，业务服务应检查用户状态，禁用用户返回 `403`。

### 3.4 分类与商品管理

#### 分类管理

- 分类树展示；支持新增、编辑、删除、启用/禁用、排序。
- 删除前检查是否含子分类或已关联 SPU。
- 禁用分类时，前台不能继续展示该分类及其商品。

现有分类 CRUD 已有基础，管理员端重点是补后台列表、状态控制和校验提示。

#### 商品管理

- SPU 分页列表：商品名、分类、品牌、主图、状态、SKU 数、创建时间。
- 按关键词、分类、状态筛选。
- 查看 SPU 与 SKU 详情。
- 管理员可新增、编辑、上架、下架商品；下架后前台列表不可见。
- SKU 支持维护价格、规格、图片、启用状态；已有订单引用的 SKU 不允许物理删除，应改为禁用。

#### 接口建议

```http
GET /api/admin/products?pageNum=1&pageSize=20&keyword=&categoryId=&status=
GET /api/admin/products/{id}
POST /api/admin/products
PUT /api/admin/products/{id}
PUT /api/admin/products/{id}/status
GET /api/admin/products/{id}/skus
POST /api/admin/products/{id}/skus
PUT /api/admin/skus/{id}
PUT /api/admin/skus/{id}/status
```

### 3.5 订单管理与履约

#### 功能

- 全平台订单分页列表，支持订单号、用户、状态、日期范围筛选。
- 订单详情：订单项、收货快照、支付信息、退款记录、库存操作日志。
- 管理员可查看所有订单；本期不允许管理员修改订单金额。
- 支持人工关闭“待支付”订单，并触发库存释放。
- 支持人工发货：录入物流公司、运单号，订单从已支付变为已发货。
- 支持确认收货：订单从已发货变为已完成。

#### 状态约定

当前代码建议统一使用：

| 状态 | 值 | 允许的后续状态 |
|---|---:|---|
| 待支付 | 0 | 已支付、已取消 |
| 已支付 | 1 | 已发货、退款中/已退款 |
| 已发货 | 2 | 已完成 |
| 已完成 | 3 | 退款中/已退款（按售后规则） |
| 已取消 | 4 | 无 |

不要在不同服务中对同一数值赋予不同含义；应新增 `OrderStatus` 枚举，替换散落的魔法数字。

#### 接口建议

```http
GET /api/admin/orders?pageNum=1&pageSize=20&orderNo=&userId=&status=&startTime=&endTime=
GET /api/admin/orders/{id}
PUT /api/admin/orders/{id}/close
PUT /api/admin/orders/{id}/ship
PUT /api/admin/orders/{id}/receive
```

发货请求：

```json
{
  "company": "顺丰速运",
  "trackingNo": "SF1234567890"
}
```

#### 表结构补充建议

在 `order_t` 增加：

```text
shipping_company VARCHAR(64) NULL
tracking_no      VARCHAR(64) NULL
ship_time        DATETIME NULL
receive_time     DATETIME NULL
close_reason     VARCHAR(255) NULL
```

为 `order_t(user_id, status, create_time)`、`order_t(order_no)` 建索引。

### 3.6 库存管理

#### 功能

- SKU 库存分页列表：SKU、商品、总库存、锁定库存、可用库存、安全库存。
- 按 SKU/商品名筛选，突出显示预警项。
- 库存补货；数量必须大于 0，并写入库存日志。
- 查看库存操作日志：初始化、锁定、扣减、释放、补货。
- 锁定、扣减、释放属于交易内部操作，管理端不能手工执行。

#### 接口建议

```http
GET /api/admin/inventory?pageNum=1&pageSize=20&keyword=&warningOnly=false
PUT /api/admin/inventory/{skuId}/add
GET /api/admin/inventory/{skuId}/logs
```

补货请求：

```json
{ "quantity": 100, "remark": "入库补货" }
```

### 3.7 支付与退款管理

#### 功能

- 支付记录分页查询：订单号、用户、金额、支付方式、支付状态、交易号、支付时间。
- 退款申请列表：订单号、申请金额、原因、状态、申请时间。
- 管理员审核退款：同意或拒绝，必须记录处理人、处理时间、处理备注。
- 退款成功后同步支付状态和订单售后状态；涉及库存返还时要先定义售后规则。

#### 接口建议

```http
GET /api/admin/payments?pageNum=1&pageSize=20&orderNo=&payStatus=
GET /api/admin/refunds?pageNum=1&pageSize=20&refundStatus=
PUT /api/admin/refunds/{id}/process
```

处理请求：

```json
{ "status": 1, "remark": "审核通过" }
```

### 3.8 操作日志

管理员修改用户状态、商品状态、库存、订单状态、退款状态时必须记录操作日志。

建议新表 `admin_operation_log`：

```text
id, admin_id, module, action, target_type, target_id,
before_data, after_data, ip, create_time
```

日志只追加、不允许前台修改；敏感字段（密码、Token）不得写入。

## 4. 管理员前端信息架构

建议在现有 `mall-front` 内新增独立后台布局，避免和买家商城的顶部导航混用：

```text
/admin
├─ /admin/dashboard       首页看板
├─ /admin/users           用户管理
├─ /admin/categories      分类管理
├─ /admin/products        商品管理
├─ /admin/products/:id    商品编辑/详情
├─ /admin/orders          订单管理
├─ /admin/orders/:id      订单详情
├─ /admin/inventory       库存管理
├─ /admin/payments        支付记录
├─ /admin/refunds         退款管理
└─ /admin/logs            操作日志（第二阶段）
```

### 4.1 推荐目录

```text
src/
├─ layouts/
│  └─ AdminLayout.vue
├─ views/admin/
│  ├─ Dashboard.vue
│  ├─ UserList.vue
│  ├─ CategoryList.vue
│  ├─ ProductList.vue
│  ├─ ProductEdit.vue
│  ├─ OrderList.vue
│  ├─ OrderDetail.vue
│  ├─ InventoryList.vue
│  ├─ PaymentList.vue
│  └─ RefundList.vue
├─ api/
│  ├─ adminDashboard.js
│  ├─ adminUser.js
│  ├─ adminProduct.js
│  ├─ adminOrder.js
│  ├─ adminInventory.js
│  └─ adminPayment.js
└─ router/
   └─ index.js
```

### 4.2 页面通用规范

- 列表页统一采用“筛选区 + 操作区 + 表格 + 分页”。
- 任何状态变更必须二次确认，成功后刷新列表。
- 删除/下架/禁用操作明确说明影响范围。
- 金额统一保留两位小数；时间统一使用 `yyyy-MM-dd HH:mm:ss`。
- 后端返回 401 时清空登录态并跳回登录页；403 时提示“无权限”。
- 订单、退款、库存等详情优先采用抽屉或详情页，不要在表格中塞入过多字段。

## 5. 后端实现规则

### 5.1 接口与权限

1. 所有管理员接口使用 `/api/admin/` 前缀。
2. Controller 从 `X-User-Id`、`X-User-Role` 读取身份，不接收前端传来的管理员 ID。
3. 统一封装 `AdminPermission` 工具或拦截器：非 `role = 2` 直接抛出 403。
4. 不能只靠网关：微服务 Controller/Service 层仍应校验管理员角色。
5. 管理端列表必须分页，禁止无条件查询全表。

建议的统一校验：

```java
private void requireAdmin(Integer role) {
    if (role == null || role != 2) {
        throw new BusinessException(ResultCode.FORBIDDEN.getCode(), "仅管理员可操作");
    }
}
```

### 5.2 分页与查询

- 请求统一使用 `pageNum`、`pageSize`，默认 `1`、`20`，最大 `100`。
- 返回使用已有 `PageResult<T>`：`records`、`total`、`pageNum`、`pageSize`、`totalPages`。
- MyBatis 查询使用动态 SQL，所有条件采用参数绑定，禁止拼接用户输入。
- 后台关键字段建立索引后再进行模糊查询和日期筛选。

### 5.3 事务与状态变化

- 关闭订单必须与释放库存、关闭支付单处于同一事务边界或具备补偿机制。
- 退款通过必须保证退款记录、支付状态、订单售后状态一致。
- 禁用商品不能影响历史订单快照。
- 删除 SKU、分类前先做业务引用检查；优先采用状态禁用，而非物理删除。

## 6. 分期开发计划

### 第一阶段：后台基础与商品运营

1. 新建 `AdminLayout`、后台路由及管理员守卫。
2. 补齐 `/api/admin/users` 用户分页与启停接口。
3. 完成分类管理、商品 SPU/SKU 管理页面。
4. 统一商品/分类管理接口的管理员权限。

**交付结果：** 管理员可安全登录后台，管理用户、分类、商品。

### 第二阶段：交易与库存运营

1. 完成订单分页、订单详情、关闭订单、发货、确认收货。
2. 完成库存列表、预警、补货和日志页面。
3. 完成支付记录、退款审批页面。
4. 统一订单状态枚举，补充订单物流字段。

**交付结果：** 管理员可以处理订单履约、库存补货和退款。

### 第三阶段：经营数据与审计

1. 首页数据看板与趋势图。
2. 管理员操作日志。
3. 超时订单自动关闭任务。
4. 关键接口测试、权限测试和异常场景测试。

**交付结果：** 管理员端具备基础运营和可追溯能力。

## 7. 开发顺序指导

建议严格按以下顺序实施：

1. 先完成管理员登录识别、`/admin` 前端路由守卫和后端 `requireAdmin`，这是所有后台功能的安全前提。
2. 实现用户分页和商品分页接口，再搭建列表页面的通用表格/分页模式。
3. 完成分类、SPU、SKU 页面；此阶段不要物理删除有关联订单的数据。
4. 补齐订单后台查询和详情，再实现关闭订单、发货、收货等状态流转。
5. 最后接入库存、退款和首页统计，因为这些功能依赖前面的订单状态和数据口径稳定。
6. 每完成一个模块都要进行“管理员可访问、买家不可访问、刷新页面不丢登录态、异常有明确提示”四项检查。

## 8. 首版验收清单

- [ ] 管理员可登录并进入 `/admin/dashboard`。
- [ ] 买家不能进入后台，也不能调用管理接口。
- [ ] 用户列表可分页、搜索、启用/禁用。
- [ ] 分类和商品可查询、编辑、上下架，前台展示同步生效。
- [ ] 订单可分页筛选、查看详情、关闭待支付单、发货、确认收货。
- [ ] 库存可查询、预警、补货并查看日志。
- [ ] 支付记录与退款申请可查询；管理员可处理退款。
- [ ] 所有关键变更生成管理员操作日志。
- [ ] 前后端错误提示明确，401/403/409/500 均有可读信息。

## 9. 下一步建议

下一步建议从“管理员后台骨架 + 路由权限 + 用户管理”开始。这一部分依赖最少，能先验证管理员角色、前端后台布局、网关鉴权和后端权限校验是否完整；基础跑通后再进入商品、订单和库存模块。
